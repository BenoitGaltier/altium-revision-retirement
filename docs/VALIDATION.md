# Acceptance procedure — isolated workspace only

## Verified during development

- Full Release build against local Designer Agile 26.11.1.28 / SDK 4.0 / .NET Framework 4.8, with warnings treated as errors.
- Version 0.1.4 adds a compiled Windows package. Nineteen isolated installer/packaging tests run under Windows PowerShell 5.1, including native build argument handling, first registration without compilation, .NET and library dependency failures, corrupt packages, rollback and preservation of other extensions. No live Altium installation is changed by these fixture tests.
- Version 0.1.5 adds the two bundled Altium runtime assemblies. Twenty-one installer/packaging cases cover installation with no Altium Developer folder, unrelated local SDK versions and bundled-DLL integrity. An isolated loader probe checks that the real assemblies and extension UI initialize using only the extracted release payload; it performs no native workspace calls.
- Version 0.1.6 preview: 76 isolated safety and inventory tests, including direct Revision ID priority, no fallback scan, folder scopes and descendant expansion, retained results, uncertain writes and targeted refresh. UI fixtures verify one modeless window, folder branch deselection, retained rows/selections after cancellation, success and lost responses, and refresh without a scan. These fixtures use fake gateways and fixture-local journals/diagnostics, never a connected workspace. The native SDK build passes; this preview has not been deployed to the user's PC and native acceptance of the new workflow is pending approval.
- The original safety coverage includes latest GUID handling, arbitrary revision labels, hidden/single revisions, lifecycle ambiguity, permissions, stale snapshots, workspace/user switches, dependency ordering and cycles, audit failures, interrupted/lost responses, postconditions and cancellation.
- The extension was registered through the native Altium Developer EPD workflow and version 0.1.3 was deployed with verified DLL hashes and loaded into the running Designer process. The window opened with the embedded Fluidra logo, English description and guide link. Only this extension's display metadata was updated; other registrations were preserved.
- Inventory regressions cover the explicit Components root, nested SDK SubFolder objects, deep parent chains, real folder GUIDs, no synthetic empty root query, empty folders, duplicate identifiers, truncated responses and count changes, uppercase native GUIDs and false zero counts. Page coverage tests include native first-page aliases, repeated pages and empty responses. English UI tests cover the main window, selection controls and confirmation dialog.
- A read-only native scan completed through the connected workspace's Components hierarchy and full item histories. It returned superseded Draft revisions for components, symbols and footprints, with the protected latest revision shown separately. Native diagnostics confirmed that deleted tombstones account for the difference between the folder count and the ExcludeDeleted listing; the verified inventory excludes them before reading histories.
- No live workspace lifecycle transition was executed by the installer or verification. Independent reconciliation against Explorer, ACL enforcement and native lifecycle rule validation remain part of the acceptance procedure below.

## Required before production use

Use a disposable workspace or test folder with components and models created specifically for this validation. Record all item/revision GUIDs and lifecycle states in Explorer before starting. Test the same Altium version and workspace plan used in production.

1. Download the compiled Windows release, close Designer, run `Install.ps1 -CheckOnly`, then `Install.ps1`, and restart. Verify that `AltiumRevisionRetirement:Manage` opens and closes without creating a server/listener or modifying workspace data. Verify the backup receipt and that unrelated extension registrations are unchanged.
2. Verify that the root is Components and that nested folders at several levels are visited. Create components, symbols and footprints with one revision and with at least three revisions. Give revision labels that do not sort lexically (for example 9 and 10, or structured schemes). Include hidden/inapplicable latest revisions and an unreleased/planned latest revision.
   - Keep the main window open and switch back to Designer. Running Manage twice must reuse one modeless window and retain its results.
   - In Folders, select a deep branch, exclude one child and verify siblings stay excluded. Confirm scans and direct lookups obey this scope. Switch workspace/user and verify the old folder scope is rejected before any query.
   - Search using both latest and older Revision IDs. All older non-Obsolete revisions of that item should appear, with no inventory scan. An unknown ID or an item outside the selected folders must not start a full scan.
3. Include older Draft revisions for all three content types, including revisions without a release date; verify that valid lifecycle transitions remain selectable and latest Draft revisions stay excluded. Compare every row to Explorer's full revision history. Verify latest means the true newest revision, including the planned/hidden cases. A single-revision item must not appear. An already Obsolete old revision must not appear.
4. Check older revisions with no Obsolete state, an ambiguous Obsolete name, no direct transition and insufficient permissions. They must be listed with a blocking reason and must not be selectable.
5. Create a latest component that references an old symbol or footprint. Selecting that model must be blocked. Then create an eligible old parent referencing an old model; explicitly selecting both must produce a parent-before-model plan. An unselected non-Obsolete parent must still block it.
6. Switch the active workspace/user after scan or after preview. The operation must stop without applying the stale plan to either workspace.
7. With a role allowed to read but forbidden to perform the transition, verify the native server rejects the event. Verify a lifecycle rule that the native Explorer validation rejects is also rejected. Do not proceed if the SDK call bypasses a rule required by your organization.
8. On one disposable eligible revision, confirm a transition with a test note. Compare the native history note, the revision GUID, all other revision states, latest state and stored model/component content before and after. Only the chosen old revision's lifecycle event should change.
9. Verify a two-item batch, user cancellation between items, a server refusal, and network interruption. No uncertain request may be retried automatically. Check the CSV `intent` and `verified` events against native history.
   - The list and unattempted selections must survive cancellation, completion and failure. Verified rows must show Obsolete, be unchecked and be blocked; uncertain rows must stay blocked until timeline review and a targeted Refresh list. Refresh must not scan unrelated folders or items, and newly latest revisions must remain protected.
10. Rescan after completion. Treated revisions should disappear. Check both old placed design instances and new-component placement for the expected lifecycle/applicability behavior.

Record the tested Designer build, workspace GUID, test role, lifecycle definition GUIDs, scan counts, before/after exports and conclusions in an internal report. Keep live audit reports, credentials and proprietary component data out of this repository. Stop deployment if any test disagrees with Explorer or the organization's lifecycle rules.
